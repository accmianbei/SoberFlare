# 架构说明

这份文档用于描述 SoberFlare 的公开高层架构。它只覆盖系统边界、产品层次和信任模型，不会公开私有代码库中的核心实现细节。

## 系统概览

SoberFlare 目前围绕五个产品层组织：

- `Identity`：地址身份与本地钱包所有权
- `Content`：信息流、帖子、评论与内容参与机制
- `Relationships`：由链上与站内上下文共同构成的可解释关系网络
- `Communication`：E2EE 私聊、E2EE 私密群与普通群聊
- `Capital Flow`：资产、转账、收款与 Swap 入口

## 客户端层

当前产品体验由 React Native 技术栈承载：

- `macOS 桌面端`：面向多栏工作流优化
- `移动端`：基于 React Native + Expo 与 Expo Router 暂未上线

客户端主要负责：

- 本地身份状态
- 钱包初始化与地址存在性
- 本地签名
- 渲染 feed、network、contacts、chat 与 profile 流程
- 将敏感秘密保存在本地设备

## 后端层

后端采用挂载在 `/api` 下的 NestJS API。

从高层来看，后端主要处理：

- 鉴权后的应用请求
- feed 与 post 相关 API
- 关系聚合与查询 API
- 通知下发
- 钱包转账构造与广播
- health 状态与 worker 协调

后端同时运行专门的 worker，用于处理加密聊天同步与关系刷新等长轮询任务。

## 数据层

SoberFlare 采用分层数据模型：

- `PostgreSQL / Supabase`：共享服务端状态的 source of truth
- `SQLite`：客户端本地缓存
- `本地安全存储`：设备秘密、钱包材料与聊天相关敏感状态

这样的拆分让共享产品状态可以放在服务端，而更敏感的用户控制材料仍保留在本地设备。

## 安全与信任边界

SoberFlare 围绕几个重要的信任假设设计：

- 钱包私钥保留在客户端本地
- 交易签名在设备上完成
- 聊天明文不作为服务端可读的产品数据
- E2EE 基础下的私聊、私密群密钥保存在本地设备
- 对于加密聊天链路，服务端只能看到地址之间的传递元数据和来往条数，无法读取明文内容

这意味着服务端负责协调产品流程，但最敏感的用户控制材料不由服务端托管。

## 关系网络层

关系层综合了：

- 多链转账上下文
- 加密聊天中地址之间的信息来往条数
- 多钱包地址下的身份归并

目标不是暴露原始关系遥测数据，而是把碎片化互动信号组织成产品可理解的社交图谱。

## 内容与分发层

内容层结合了：

- 多频道 feed 入口
- 帖子创建与互动流程
- 链上参与机制

这个公开仓库不会披露内部完整的排序或分发实现。高层来看，这套系统是在探索 AI 时代下更好的信息分发方式，让真正有价值的内容不只是出现在时间线上，而是能够持续地被看见。

## 公开层与私有层

这个仓库是公开文档层。

它主要展示：

- 产品方向
- 架构边界
- release 状态
- 对外展示材料

完整的生产实现不会在黑客松评审阶段通过这个公开仓库直接披露。
